This page summarizes Bun benchmark runs for Knitting `0.1.24` on
`bun 1.3.6 (arm64-darwin)`, recorded in March 2026.

## IPC (Bun)
This benchmark measures round-trip communication between the main thread and
workers using different transports.
Knitting has the lowest overhead in this setup:

- `1` message: Knitting is about `4.4x` faster than worker `postMessage`, `8.1x` faster than WebSocket, and `16.5x` faster than HTTP.
- `25` messages: Knitting is about `5.5x` faster than worker `postMessage`.
- `50` messages: Knitting is about `5.3x` faster than worker `postMessage`.

## Knitting vs Worker (Bun)
These charts compare the same payload types sent through Knitting and Bun workers.

### One message
With a single value per call, Knitting is faster in these measurements:

- For small primitives, Knitting is roughly `~6-17x` faster than workers.
- For string/array/object payloads, Knitting is usually around `~4-6x` faster.
- For larger payloads, Knitting still holds a clear advantage (for example, big object: `3.97 µs` vs `16.38 µs`, about `4.1x` faster).

### 100 messages
At `100` messages per iteration:

- Primitive payloads are `~7-9x` faster with Knitting.
- Heavier payloads are about `~3.7-3.9x` faster.
- Batching improves throughput for both, but Knitting has lower overhead across the tested payload types.

## Call growth throughput (Bun)
This benchmark increases payload size from `32 B` up to `1,048,576 B` (1 MiB) and reports
the time per batch with `batch=64`.

Using the `1048576 B` row (`avg`) from the `batch=64` run, one-way transfer throughput is:

- `string`: `5.66 ms/iter` -> `11.86 GB/s`
- `Uint8Array`: `4.14 ms/iter` -> `16.21 GB/s`

Interpretation:

- Bun remains the fastest runtime in this 1 MiB batch test for both string and binary payloads.
- The `Uint8Array` path clears `16 GB/s` one-way equivalent in this run, with strings close to `12 GB/s`.

## Efficiency under heavy tasks (Bun)
<HeavyTaskPrimeTransferCaution />

This stress test computes prime numbers over a large range, then serializes and parses large JSON payloads:

```ts
const N = 10_000_000; // search range: [1..N]
const CHUNK_SIZE = 250_000;
```

Even under this heavier workload, parallel workers scale well:

- `main + 1 extra thread`: `~1.8x` faster than main only.
- `main + 2 extra threads`: `~2.5x` faster than main only.
- `main + 3 extra threads`: `~3.3x` faster than main only.
- `main + 4 extra threads`: `~3.8x` faster than main only.

## All types in Knitting
This benchmark covers primitives, structured values, collections, typed arrays,
errors, dates, symbols, and promise arguments. It also compares static and
dynamic payload allocation.
Results are reported for count `1` and count `100` to show both per-call latency and batched throughput.

Quick takeaways:

- At count `100`, primitive payloads are usually in the `~16-25 µs` range, while heavier structured/collection payloads are often `~60-270 µs` with occasional larger spikes.
- The static payload path is usually around `~1.3x-3.1x` faster than dynamic allocator paths (for example: string `~1.8x`, JSON `~2.1x`, `Uint8Array` `~1.3x`, symbol `~3.1x` at count `100`).
