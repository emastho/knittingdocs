hardware and Knitting versions.

## Put a second core to work

Measured on 24–25 August 2026 with Bun 1.4.0 and Knitting commit `6c0e56d`,
on an Intel Xeon Platinum 8168 server with 16 dedicated cores, running Ubuntu
24.04. A separate machine generated the load. The [report](/documents/hono-16core-benchmark.md)
has the setup and individual runs.

CPU-heavy JavaScript on one event loop runs on one thread. Moving those routes
into a Knitting worker lets another core take part while the main thread keeps
serving requests.

The test is a Hono server with three routes. `/ssr` renders React, `/jwt` signs
a token, and `/ping` returns a small JSON object. With Knitting, `/ssr` and
`/jwt` run in one worker and `/ping` stays on the main thread. Both servers
received 2,000 requests per second on each route.

<CompareBars

  legend={{ baseline: 'Hono only', knitting: 'Hono with one Knitting worker' }}
  caption="p99 response time at 6,000 requests per second in total."
  groups={hono.latencyGroups}
/>

`/ping` p99 fell by {hono.reductions[0]}%, and `/ping` never enters the pool. Its requests had
been waiting behind renders and signatures on the same thread. `/ssr` p99 fell
by {hono.reductions[1]}% and `/jwt` by {hono.reductions[2]}%.

Both servers met the offered request rate with 100% success, at approximately
the same measured CPU usage:

  caption="CPU used by the server process during the same runs."

A repeat of the one-worker run recorded {repeatCores} cores, also close to

Under saturating load, the same change raised total throughput from {hono.saturation[0].rps.toLocaleString("en-US")} to
{hono.saturation[1].rps.toLocaleString("en-US")} requests per second, and CPU use
from {hono.saturation[0].cores} to {hono.saturation[1].cores} cores.

## CPU-heavy work spreads across threads

Measured in March 2026 with Knitting `0.1.24` on an Apple M3 Ultra:
Node.js 24.12.0, Deno 2.6.6 and Bun 1.3.6, on macOS arm64. Bars show
average elapsed time from the saved reports.

The task finds the primes up to 10,000,000 in chunks of 250,000 and returns
each chunk's primes to the main thread. The main thread takes chunks too, so
four extra threads means five threads working.

<CompareBars
  unit="ms"
  legend={{ baseline: 'Main thread only', knitting: 'Main thread plus Knitting workers' }}
  caption="Time to finish the whole range on Node.js."
  groups={primeGroups}
/>

With four extra threads the run finished {primeSpeedups.node}× faster on Node.js,
{primeSpeedups.deno}× on Deno and {primeSpeedups.bun}× on Bun. Five threads would
ideally finish in one fifth of the time. Returning every chunk's primes to the
main thread adds work, so this test measures computation and transport together.
The [reports](/benchmarks/results/#runtime-reports) include the other worker counts.

## A typesetting workload scales across cores

The open-source [knit-tex](https://github.com/mimiMonads/knit-tex) project
typesets a 216-page copy of *Pride and Prejudice* to PDF. On an Intel Core
i5-1135G7 with four physical cores, knitting x4 reduced the median of five warm
runs from 427 ms to 229 ms on Node 24.19.0 (1.86×), and from 449 ms to 254 ms
on Bun 1.4.0 (1.77×). In both runtimes, pool output hashes matched that
runtime's main-thread output.

The faster runs used more CPU time: 871 ms versus 509 ms on Node, and 1,266 ms
versus 607 ms on Bun. The cold full-document run and fresh-process CLI runs
were slower with four workers than on the main thread. Pool startup and worker
warm-up can outweigh parallel work when the executor is used only once.

The project also tested work stealing with a mixed batch of 2,115 paragraph
tasks. At four workers, Node finished 9.7–23.3% sooner across three seeds;
Bun's results ranged from 5.5% slower to 17.5% faster. These runs support a
workload-specific benefit, not a general speedup guarantee. The timer-gap
measurements in the reports are responsiveness proxies, not request latency.
The [knit-tex README](https://github.com/mimiMonads/knit-tex#benchmarks)
explains the method and limits; the [Node full-document report](https://github.com/mimiMonads/knit-tex/blob/main/output/bench/node-24.19.md),
[Bun full-document report](https://github.com/mimiMonads/knit-tex/blob/main/output/bench/bun-1.4.0.md),
and [mixed-batch reports](https://github.com/mimiMonads/knit-tex/tree/main/output/bench)
contain the measurements.

## Binary round trips are comparable to Tokio

Measured in March 2026 with Knitting `0.1.36` on an AMD Ryzen 7 4700U,
running Ubuntu 23.10 x86_64. This is a separate run from the M3 Ultra tests
above. The [Tokio report](/benchmarks/tokio/#full-raw-report) records the sources
and methodology; runtime versions were not recorded in that report.

The Rust program clones a `Vec<u8>`, sends it to a Tokio task
over a channel, and gets a second clone back, with one worker thread. Knitting
does the same round trip with a `Uint8Array`, using preallocated shared memory.
This compares the two copying paths, including allocation and worker coordination;
it does not measure the speed of copying bytes alone.

<CompareBars
  unit="ms"
  legend={{ baseline: 'Tokio (Rust)', knitting: 'Knitting' }}
  caption="Time for 100 round trips of a 256 KiB payload."
  groups={copyGroups}
/>

From 32 KiB to 512 KiB, Knitting on Bun and Node.js took {copyRange.fastest}% to
{copyRange.slowest}% less time than Tokio. On Deno it ranged from
{copyRange.denoLess}% less to {copyRange.denoMore}% more.

From 1 KiB to 16 KiB, Tokio was up to {smallCopyLead}× faster. At 1 MiB it was
{largeCopyLead} faster. The [Tokio page](/benchmarks/tokio/#how-the-payload-size-changes-things)
has every size and explains how copying differs from its separate shared-ownership test.

These results describe the tested configurations. Measure your workload on your
target hardware; payload size, runtime and worker count can change the result.
