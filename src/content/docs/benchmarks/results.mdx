## How to read the reports

The M3 Ultra tests were recorded in March 2026 with Knitting `0.1.24`, on
macOS arm64. Each report names its runtime and gives average, minimum, p75,
p99 and maximum elapsed time. The performance charts use the averages.

A count of `100` means 100 calls in flight, and the reported time is for the
whole batch. Dividing by 100 gives amortized time per call, useful for comparing
throughput. It does not tell you how long an individual call waits.

The empty-call test measures a call and its reply with one worker. The payload
comparison repeats that trip with different values. The CPU-heavy test searches
for primes up to 10,000,000 in chunks of 250,000, with the main thread taking
chunks too. Returning the primes adds serialization and parsing work to the
computation.

The Markdown reports below are the sources for these charts. The separately
saved JSON exports contain different measurements and are not substituted for
them. These historical runs have not been repeated on the current release.

## Other measurements

### Typesetting a long document

The [knit-tex benchmark](https://github.com/mimiMonads/knit-tex#benchmarks)
typesets *Pride and Prejudice* (2,118 paragraph tasks, 216 pages) with either
the main thread or a Knitting pool. The recorded machine has four physical
cores and eight logical CPUs; the reports use Node 24.19.0 and Bun 1.4.0 with
Knitting 0.1.73. Each warm result is the median of five runs on a reused
executor. The source reports include cold runs, CPU time, timer gaps, and
output-hash checks:

| Runtime | Main-thread warm | Knitting x4 warm | Speedup | CPU time, main → x4 |
| --- | ---: | ---: | ---: | ---: |
| Node 24.19.0 | 427 ms | 229 ms | 1.86× | 509 → 871 ms |
| Bun 1.4.0 | 449 ms | 254 ms | 1.77× | 607 → 1,266 ms |

Four workers improved warm completion time while using more total CPU time.
Cold full-document and fresh-process CLI results were slower with four workers
than on the main thread. The benchmark ran on one machine; its saved reports
contain medians, not raw samples or confidence intervals. The mixed-batch
work-stealing runs use three seeds and show mixed results on Bun. See the
[Node report](https://github.com/mimiMonads/knit-tex/blob/main/output/bench/node-24.19.md),
[Bun report](https://github.com/mimiMonads/knit-tex/blob/main/output/bench/bun-1.4.0.md),
and [project README](https://github.com/mimiMonads/knit-tex#benchmarks) for
methodology and additional comparisons.

### Loopback WebSocket and HTTP

The IPC reports above compare Knitting with worker messaging, loopback
WebSocket and HTTP round trips. Across those runs, Knitting was {ipcRatioRange("websocket")}
faster than WebSocket and {ipcRatioRange("http")} faster than HTTP. These transports serve
different purposes: a worker call does not replace a network connection.

## Run the benchmarks

The M3 Ultra harness lives under `bench/` in
[`mimiMonads/knitting`](https://github.com/mimiMonads/knitting). The historical
runs used `bench/latency.ts` for empty calls and `bench/withload.ts` for primes.
Run the driver from the repository root:

```bash
./run.sh
```

Results are written to `results/`. Use `./run.sh --json` to emit JSON. To
reproduce historical results, use the measured release and its harness; running
the current checkout measures the current implementation.

The [Hono report](/documents/hono-16core-benchmark.md) includes the server in
Appendix B and harness in Appendix C. The Tokio comparison and newer payload
suite live in [`knitting-vs-tokio-bench`](https://github.com/mimiMonads/knitting-vs-tokio-bench).
See [Payload types](/benchmarks/payload-types/#run-it-yourself) for copying
committed runs into the docs.
