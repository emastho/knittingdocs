This example derives password hashes with PBKDF2-SHA256 and verifies them using
constant-time comparison. It is the most expensive per-call workload in the
validation examples because PBKDF2 deliberately requires substantial computation.

## How it works

1. Generate a random salt per password.
2. Derive a hash using `PBKDF2-SHA256` via Web Crypto.
3. Store the result as a compact record: `algorithm$iterations$keyBytes$salt$hash`.
4. Verify login attempts by recomputing the hash and comparing it in constant time.

The benchmark uses `Uint8Array` payloads to reduce serialization noise in hot loops.

Three files:

- `salt_knitting.ts` -- runs salting + verification in host and Knitting modes
- `utils.ts` -- hashing, verification, and fast-path packet functions
- `bench_salt_hashing.ts` -- host-vs-worker benchmark with `mitata`

## Example record shape

The stored credential format is intentionally compact:

```txt
pbkdf2-sha256$600000$32$<salt-base64url>$<hash-base64url>
```

At a high level the flow is:

```txt
password -> derive PBKDF2 hash with random salt -> store compact record
login attempt -> derive again with stored salt -> constant-time compare
```

That makes the worker boundary simple: small input, small output, expensive CPU work in the middle.

The example uses built-in Web Crypto APIs, so no extra crypto package is required.

(`host`) with worker task calls (`knitting`). The high PBKDF2 iteration count
makes dispatch overhead small relative to the work in each call.

## The ideal offload candidate

Password hashing combines independent calls, small inputs and outputs, and
substantial CPU work. This makes it a useful workload for comparing host and
worker execution, especially during bursts of logins or signups.
